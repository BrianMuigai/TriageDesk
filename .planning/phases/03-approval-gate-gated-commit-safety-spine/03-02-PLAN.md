    - Test 4: a simulated crash after the queue write but before acknowledgement, followed by a retry, still yields one row — the test's comment attributes crash-safety to the idempotency key (`case_id` + content hash), with any store transaction as belt-and-braces only (D-06).
  </behavior>
  <action>
Create `store/queue.py` with the ONE idempotent write path. Add a small helper (e.g.
`content_hash(case_id, priority)`) that hashes ONLY immutable case content — `case_id` plus the scored
fields the write depends on (colour, target, the ordered citation/triggered-rule content, used vitals) —
through `core/hashing.hash_value`; it MUST exclude the approval timestamp and any wall-clock value
(D-06, Pitfall 14). The upsert is keyed by (`case_id`, `content_hash`): if a row with that key exists,
return the existing row unchanged (no second insert); otherwise insert one row with the next queue
position. **Crash-safety is the idempotency key itself** (`case_id` + immutable content hash): a retry
re-derives the same key, so the upsert is a no-op and a second row cannot appear — this is the actual
mechanism, and it does not rest on a transaction primitive the borrowed server does not expose (its tool
set has no transaction call). The queue row and its approval audit record are written through the one
authoritative store; because the audit append runs in the commit call's interceptor (Plan 03-03)
immediately after the queue write, the narrow window between the two is **detected and reconciled**, not
silently accepted: `store/audit.reconcile(store)` (Plan 03-03) reports any queue row lacking its matching
approval audit record, and re-issuing the same idempotent commit completes the missing append (D-09,
Pitfall 14). Treat any store-level transaction as belt-and-braces only. Never default or synthesise a value.
</action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| commit node -> commit_priority | The approval token is untrusted until validated; validation precedes any store access. |
| commit_priority -> borrowed MCP server | Third-party code holds the queue; it receives only the idempotent key and immutable content. |
| store -> core/hashing | The idempotency key must be stable; a volatile field in the key would defeat idempotency. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-06 | Tampering | commit_priority -> queue | high | mitigate | The write is idempotent on (`case_id`, immutable content hash); a repeat or crash-retry yields exactly one row (GATE-03, D-06). |
| T-03-07 | Tampering | idempotency key | high | mitigate | The hash covers immutable case content only; the approval timestamp never enters the key, so a retry cannot churn it into a duplicate (Pitfall 14). |
| T-03-08 | Repudiation | queue vs audit stores | high | mitigate | Crash-safety is the idempotency key (`case_id` + content hash): a retry re-derives the key, so the queue write is a no-op and the missing audit append completes. The borrowed server has no transaction primitive, so the narrow queue-write/audit-append window is detected and reconciled by `store/audit.reconcile` (Plan 03-03) rather than assumed atomic (D-09, Pitfall 14). |
| T-03-09 | Elevation of privilege | commit_priority | critical | mitigate | The token is validated and the refusal returns before any store call; no path reaches the store without a valid named approval (GATE-02, D-05). |
| T-03-10 | Tampering | borrowed MCP server | medium | mitigate | The store depends on a narrow protocol behind the tool interface; a World-B swap touches one module (D-10, D-13, SOLID: L). |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | The borrowed server is pinned (`mcp-sqlite@1.0.9`) and was legitimacy-reviewed in Phase 1; no new package is installed here. |
