# Plan 23-01 — The `plan` node and the bounded investigation loop

## Objective

Wire the owner-approved topology from `23-CONTEXT.md` into the shipped graph: an
investigation loop that runs **before** the frozen safety kernel, bounded by
`MAX_INVESTIGATION_STEPS`, with a pure monotone merge and no way for an investigation action
to reach `score`, the gate or the commit.

```
START → ingest → emergency_check ─┬─(fast)──────────→ retrieve
                                 └─(normal)→ normalize → retrieve
retrieve ─┬─(emergency_verdict.fired)────→ finish_investigation
          └─(otherwise)───────────────────→ plan
plan ─┬→ gather_evidence → plan
      ├→ ask_question   → retrieve
      ├→ re_extract     → retrieve
      └→ finish_investigation → score
```

**The critical property:** `predecessors("score") == {"finish_investigation"}` — the emergency
arm enters the kernel *through* `finish_investigation` too, so the structural claim is exact.

## DRY + SOLID

- **DRY** — the four action names are the `PlanAction` members and the node names; the
  router's edge map is *derived* from the enum, so a new action cannot be added in one place
  and forgotten in another. `parse_tool_result` remains the ONE tool-payload parser.
  `scorer.case_field` remains the ONE parameter→field binding. No SATS value is inlined.
- **SOLID: S** — each node does one thing: `plan` decides, `gather_evidence` retrieves,
  `ask_question` asks, `re_extract` re-normalises and merges, `finish_investigation` is a
  no-op marker. **O** — a new investigation action is a new `PlanAction` member + a new node,
  never an edit to `score`. **I** — the planner's input is the narrow `InvestigationState`
  (`extra="forbid"`), unchanged. **D** — nodes still receive only the injected `ToolMap`.

## Tasks

1. **`core/schema.py` — `InvestigationFacts`.** Declare the typed accumulator beside
   `InvestigationState`: `steps: int`, `history: list[PlanAction]`, `answers: list[str]`,
   `guard_overrides: int`. It carries no colour, priority, approval or queue field (ADAPT-04).
   Because `graph/build._allowed_msgpack_modules` derives its allowlist from `core.schema`,
   the checkpointer can persist it with no second list to maintain.

2. **`core/merge.py` (new, pure).** `merge_monotone(current, extracted) -> CaseInput` — iterate
   `CaseInput.model_fields` and take the extracted value **only when the current value is
   `None`**. No model, no store, no SATS value. `extra`-free, no validator.

3. **`graph/state.py`.** Add `plan: PlanDecision | None`, `investigation: InvestigationFacts`,
   `nurse_answers: list[str]`. Each has exactly one writer (documented in the field comment):
   `plan` writes `plan`/`investigation`; `ask_question` writes `nurse_answers`.

4. **`graph/planning.py` (new).** The five node factories, each returning a partial update:
   - `plan` — builds `InvestigationState` from typed state (complaint, retrieval status,
     candidates, questions, missing scored vitals, has-evidence, step/budget derived from
     `InvestigationFacts.steps`, clarification round, history), calls the injected
     `plan_next_step`, stores `plan` + the updated `investigation`. It is the ONE writer of
     `steps`/`history`/`guard_overrides` — the decision is recorded where it is made.
   - `gather_evidence` — calls `retrieve_evidence`, writes `evidence` only.
   - `ask_question` — calls `request_clarification(candidates=...)`; on `accepted` appends the
     answers to `nurse_answers` and increments `clarification_round`; on
     `declined`/`cancelled`/`unavailable` appends nothing (the outcome is recorded on the
     decision span and in the tool's audit record).
   - `re_extract` — calls `normalize_case` with the raw note and merges the result through
     `merge_monotone` (ADAPT-07). The planner's hint is recorded on the decision, never
     injected into the note: planner-authored text must not enter the evidence path.
   - `finish_investigation` — a pure no-op marker that emits the final decision fact.
   - `missing_scored_parameters(case)` — the projection the planner reads; a guard test pins
     it to `scorer.score_priority(case).missing_vitals` so the two cannot drift.

5. **`graph/nodes.py`.** `retrieve` re-matches against the note **plus the nurse's answers**
   (`_rematch_note`), so an answer can resolve an ambiguity; `make_nodes` merges the planning
   nodes in (one lazy import inside the composition function, so `planning` may depend on
   `nodes`' primitives without a module-level cycle).

6. **`graph/build.py`.** Add the five names to `TRACER_NODES`; add `route_after_retrieve` and
   `route_after_plan`; replace the plain `retrieve -> score` edge with the conditional edges
   from the topology; export both routers.

7. **Offline determinism.** `evals/tools._tool_map` and `tests/conftest.build_graph_tools`
   answer `plan_next_step` without a model in offline mode (`planner.default_plan`) — the
   offline gate must never reach Ollama. Real mode keeps the shipped tool.

8. **Tests.** `tests/test_merge_monotone.py` (field-by-field, contradiction case) and
   `tests/test_graph_planning.py` (adaptive happy path, gather path, re_extract fills a
   missing vital and never overwrites a stated one, ask-question refusal appends nothing).
   Update `tests/test_emergency_bypass.py`'s executed-order constants for the new nodes.
