# Phase 20 · Plan 03 — Guard degradation, boundaries and the purity proof

## Objective

Prove the one-way safety property: a model proposal can be wrong in every way and the system still
lands on the deterministic default. Nothing in this plan changes production code.

## DRY / SOLID compliance (iron-clad, `docs/CONVENTIONS.md`)

- **DRY** — one degradation table drives every cause (parametrised over a single fixture factory),
  and the purity test reuses `test_purity.py`'s existing `_forbidden_in_file` helper instead of a
  second import scanner.
- **DRY** — the tests read the action set from `PlanAction` and the bound from
  `MAX_INVESTIGATION_STEPS`; no action string or budget literal is restated.
- **SOLID:S** — the tests exercise the policy function directly; no test re-implements admissibility.
- **SOLID:O** — the matrices are parametrised, so a new action or a new cause is one row, not a new
  test function.

- No proposal can widen the action set, in any state (ADAPT-02/04/06).
- `core/planner.py` purity is a named, enforced contract (D-13).
