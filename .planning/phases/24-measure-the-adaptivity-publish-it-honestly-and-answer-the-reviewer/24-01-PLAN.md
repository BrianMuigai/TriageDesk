# Plan 24-01 — Two arms, and the facts that measure them

## Objective

Make the adaptive-vs-baseline comparison **possible and honest** without touching the safety
kernel. The baseline arm is the v1.2 path (`retrieve -> finish_investigation -> score`): no
planner, no model proposal, no investigation. The adaptive arm is today's shipped graph. The
harness records, per run, what the planner actually did — steps, the action sequence, whether
the guard overrode a proposal, the elicitation outcome, and whether the emergency bypass fired
— so the published comparison is derived from measurement, not narrative.

## DRY + SOLID

- **DRY** — the two arms are one builder with one switch, not two graph modules: the topology
  is declared once and the baseline simply omits the planner nodes and its edges. The arm is
  named once (`planner: bool`) and threaded from the CLI through `run_eval` to `build_graph`;
  no second copy of "which graph" exists. `PlanAction` remains the ONE action vocabulary; the
  harness records its `.value`, never a re-typed string.
- **SOLID: S** — `build_graph` composes; `_run_case` measures; `analyse` aggregates. The
  baseline switch changes composition only and adds no branch to any node.
- **SOLID: O** — a third arm (a future `planner="ask-only"`) is a new value at the same seam,
  not an edit to every node.
- **SOLID: L** — the baseline graph is substitutable for the adaptive one at every call site
  (`run_eval`, the CLI, the tests): both expose the same state contract and the same kernel
  terminals, so a consumer cannot tell which arm it was handed except by the facts it reads.
- **SOLID: D** — the harness still depends on the injected tool mapping, never on an adapter;
  the arm is a composition parameter, not a concrete import.
- **No SATS value is inlined**; the new analysis block reads only recorded facts.

## Tasks

### Task 1 — `planner` switch on `build_graph`

`type="auto"`

- Add `planner: bool = True` to `build_graph`. With `planner=False`:
  - do **not** add `plan`, `gather_evidence`, `ask_question`, `re_extract` to the graph;
  - wire `retrieve -> finish_investigation` with a plain edge (the emergency arm and the
    normal arm both land there);
  - keep every kernel node and edge byte-identical.
- Update `route_after_retrieve`'s docstring to name the baseline arm.
- Add a structural test: on both arms `predecessors("score") == {"finish_investigation"}` and
  `predecessors("commit") == {"approval_gate"}`; with `planner=False` the node set excludes
  the four planner nodes.

**Verify:** `uv run pytest -q tests/test_eval_adaptive.py -k graph`

### Task 2 — record the per-run investigation facts

`type="auto"`

- Add `elicitation_outcome: str | None` to `TriageState`, written by `ask_question` on every
  outcome (not only an acceptance), so the harness can report the four-way outcome without
  re-deriving it from the audit log.
- Extend `ReportCase` with default-empty, index-aligned lists:
  `investigation_steps: list[int | None]`, `plan_actions: list[list[str]]`,
  `guard_overrides: list[int]`, `elicitation_outcomes: list[str | None]`,
  `emergency_bypass: list[bool]`.
- Populate them in `_run_case` from the final state (`investigation.steps`,
  `investigation.history`, `investigation.guard_overrides`, `elicitation_outcome`,
  `emergency_verdict.fired`). An errored run contributes `None` / `[]` / `0` / `None` /
  `False`, staying index-aligned with `outcomes` and `latency_s`.
- Do **not** add them to `_digest_payload`: they are volatile run facts like `latency_s`, and
  the digest contract must not move for an older report.

**Verify:** `uv run pytest -q tests/test_eval_report.py tests/test_eval_adaptive.py`

### Task 3 — the `adaptive` analysis block

`type="auto"`

- Add `Adaptive` to `evals/report.py` and `Analysis.adaptive: Adaptive = Field(default_factory=Adaptive)`.
- In `analyse`, compute: `runs_with_investigation` (runs whose `investigation_steps` is a
  positive int), `mean_steps` over measured steps, `max_steps`, `action_counts`,
  `guard_override_rate` (overrides ÷ runs with investigation), `elicitation_counts`,
  `emergency_bypass_cases`.
- A baseline report (all `None`) yields an all-zero block, never an error.

**Verify:** `uv run pytest -q tests/test_eval_adaptive.py -k analysis`

### Task 4 — `run_eval(..., planner=...)` and `triagedesk eval --no-planner`

`type="auto"`

- Thread `planner: bool = True` through `run_eval` → `_run_case` → `_run_once` →
  `build_graph`.
- Record the arm on the report (`planner: bool = True` on `Report`, defaulted so older
  reports validate).
- Add `--no-planner` to `triagedesk eval` (`dest="planner", action="store_false"`).
- Test: `run_eval(..., planner=False)` on one case writes `planner=False`, all
  `investigation_steps` are `None`, and the run still delivers the same colour as the
  adaptive arm on that case.

**Verify:** `uv run triagedesk eval --cases evals/cases --case E-01 --runs 1 --offline --no-planner --report /tmp/opencode/arm.json`
