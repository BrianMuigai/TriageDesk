How the desk, the core, and MCP connect

The desk is the demo surface. The core is the clinical solution. The MCP server is the station integration path. They share one set of tool implementations — not one transport.

1 · Demo surface

Desk (this page)

A browser-facing workspace: conversation, structured intake, approval gate, waiting room and handover.

  • Runs the core graph in-process; it does not call the MCP server over the wire.
  • Binds loopback only, makes no external request, and has no authentication.
  • Has no queue write of its own: the only route is the named approval gate → the gated commit tool.

Protocol: HTTP form POST (loopback) → server-rendered HTML

2 · Solution

Core (the clinical logic)

The deterministic kernel plus the LangGraph run: normalize → match → score → evidence → confidence → plan → approval gate → commit → handover.

  • SATS thresholds and discriminators live only in data/*.yaml.
  • The model may structure a note or propose an investigation step; it never computes a colour or approves.
  • The committed queue row and the hash-chained audit record are authoritative.

Protocol: in-process Python calls to the shared tool implementations

3 · Integration

MCP server (station link)

The owned triagedesk-triage server exposes the core as nine MCP tools to a hospital station app or agent.

  • Transport: stdio, JSON‑RPC 2.0; the client runs initialize → tools/list → tools/call.
  • Mid-call questions use MCP elicitation; a question is never an approval.
  • Storage: the borrowed mcp-sqlite@1.0.9 server holds the queue and audit chain.

Protocol: MCP over stdio (JSON‑RPC 2.0)

The wire, in order

  1. Browser → desk HTTP form POST on loopback, with the per-server CSRF token; the response is server-rendered HTML.
  2. Desk → core An in-process tool map: the same nine implementations the MCP server registers, reached without a subprocess.
  3. Station app → MCP server MCP JSON‑RPC over stdio: discover the tool list, then call a tool by name with a typed argument object.
  4. MCP server → borrowed store MCP JSON‑RPC over stdio to the pinned mcp-sqlite@1.0.9 server. Queue and audit writes go through the gated commit only.
  5. Station app ← handover The triagedesk.handover/1 JSON projection: a read-only machine-readable twin of the clinical handover.

Nine tools on the MCP surface

  • normalize_casenote → typed case
  • score_prioritydeterministic SATS colour
  • match_discriminatorsclosed-set complaint match
  • retrieve_evidenceattributed SATS excerpts
  • assess_confidencedeliver / clarify / defer
  • raise_recheck_flagserial-vitals second look
  • plan_next_stepmodel proposes, guard disposes
  • request_clarificationmid-call question, bounded
  • commit_prioritythe only queue-affecting tool

The desk does not call these over the wire; it calls the same implementations in-process. A station app is the MCP client.

What this means for integration

Use the MCP server when another hospital station needs to call triage. Do not scrape the desk page: it is a loopback demo with no authentication, and its HTML is presentation, not a contract.

The stable integration outputs are the MCP tool contracts and the triagedesk.handover/1 JSON projection. The committed queue row and the audit chain win on any disagreement.

Install the server into a harness with uv run python scripts/install_mcp.py --harness <key> --write; the operator runbook is docs/MCP.md.
